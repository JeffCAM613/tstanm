PART 1 - DECISIONS
==================

Q1. NODES ON OTHER SCREENS
--------------------------
What: a structure node whose ecran is neither 'w_tiers' nor
'w_compte_banque', and whose code is also a client code (a tiers code, a
compte_banque code, or the code of a w_tiers or w_compte_banque node).
Example: node ABC, structure Entite, ecran w_autre - and ABC is a tiers code.

Legacy: never touches it. Every structure.code and structure.description
update is limited to Entite/w_tiers, Compte/w_tiers or Compte/w_compte_banque
(lines 104, 147, 764, 807, 1424, 1466, 2083, 2115). Nothing is reported.

v4 today: never touches it either. But it FLAGS it: REVIEW in the run log,
and the verification answers REVIEW REQUIRED (exit 3) instead of PASS,
because the client code is still visible in that node.

Options
  A. Leave it and stop flagging it; show a count only.     <- recommended
  B. Keep flagging it (today).

Why A: the same result as legacy, and the screen is the application's own
statement of what a node is. The risk: if such a node really is the same
client, its code stays visible. The count keeps that in sight.

Q1b. A parent text that is a w_tiers node AND a node on another screen
(a child whose pere = ABC, where ABC is both). Today: left and flagged.
Recommended with A: the party's value - a node on another screen is not
considered as a parent.

How often: diagnostics section 5, column OTHER_HOLDING_IDENTIFIER.

Q2. A PARENT THAT IS BOTH A PARTY NODE AND AN ACCOUNT NODE
----------------------------------------------------------
What: text SHRD is a w_tiers node (a party) AND a w_compte_banque node (a
bank account). A child node has pere = SHRD. After the run the two SHRD
nodes have different values (E_... and CB_...); the child can follow only
one of them.

Legacy: decided by the CHILD's own classification, on any screen:
  line 155   Entite branch        pere = E_  for children classified Entite
  line 815   Portefeuille branch  pere = P_  for children classified Entite
  line 1474  Tiers branch         pere = T_  for children classified Compte
  line 2205  Compte branch        pere = CB_ for children classified Compte
So: a child classified Entite gets the party's value; a child classified
Compte gets the account's CB_ (T_ if SHRD is also a counterparty node); any
other child is left unchanged.

v4 today: left unchanged and flagged REVIEW.

Options
  A. Like legacy: by the child's classification.
  B. By the child's screen:                                <- recommended
       child on w_tiers .......... the party's value
       child on w_compte_banque .. the party's value, if diagnostics
                                   section 6 shows that bank-account nodes
                                   normally sit under party nodes;
                                   otherwise flagged
       child on another screen ... unchanged (see Q1)
  C. Keep flagging (today).

Why B: a node on w_tiers belongs to the party tree, so its parent is the
party. Under A, a counterparty node (Compte on w_tiers) under the entity
SHRD is pointed at the bank account SHRD instead - the specification calls
that legacy filter "weaker" (its section 4). A and B agree for children
classified Entite.

How often: diagnostics section 8 (these children, by screen and
classification); section 6 (where bank-account nodes normally sit).

Q4. val_bank_account.code - PARTY OR BANK ACCOUNT?
--------------------------------------------------
Legacy updates it only in the three party branches (lines 666, 1326, 1985):

accounts, and v4 follows v3: an account code there gets its CB_, a party
code is left - and verification FAILs the column ("original of the OTHER
domain remains").

  A. BANK_ACCOUNT (v3, v4 today).
  B. PARTY (legacy).
  C. MIXED - both, as in Q3.
Recommendation: decide from diagnostics section 7, row
val_bank_account.code. Mostly account codes: A. Mostly party codes: B.
Both kinds: C.
